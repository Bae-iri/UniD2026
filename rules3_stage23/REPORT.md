# rules3 이후 잔여 오류와 2↔3 보정 재검증

## 이번 작업 범위

사용자가 요청한 '3번: rules3 이후 2↔3 개선 비교'를 실행했다. 팀원 MLP는 제외하고 사용자가 진행하던 센서 상·하한/확률 보정과 이전에 구현한 확인 상태 유지 규칙을 비교했다. 원본 B, rules3 코드와 제출은 변경하지 않았다. 새 MLP나 별도 전문가도 만들지 않았다.

**0.93 제출인 `final_submit/submission_rules3.csv`를 `final_rules3.py`의 원래 제출용 학습 범위로 재생성하여 바이트 단위 일치를 확인했다.** 새 후보를 Test에 적용하거나 제출하지 않았다. Test 접근은 기존 기준 파일의 재현 확인에만 사용했다.

이번 내부 평가의 하한·상한·온도 확률표는 **원래 fit 62개 실험에서만** 추정하여 dev 16개/validation 19개에 똑같이 적용했다. 최종 배포 파일은 원래 코드대로 train+validation(E16 제외)에서 하한을 추정하므로 두 학습 범위를 혼용하지 않는다. 내부 점수는 공개 점수 0.93과 별개다.

## 1. 지금 오류의 대부분이 2↔3인가?

| 실제→예측 | dev | validation E16 제외 |
|---|---:|---:|
| 3→2 | 275 | 168 |
| 2→3 | 149 | 49 |
| 5→6 | 50 | 111 |
| 6→5 | 45 | 53 |
| 5→4 | 61 | 15 |
| 4→5 | 26 | 33 |
| 전체 오류 | 618 | 446 |
| 2↔3 오류 합계 | **424 (68.6%)** | **217 (48.7%)** |

두 split을 E16 제외로 합치면 전체 1064건 중 641건, **60.2%가 2↔3**이다. 따라서 사용자 판단은 이 범위에서는 맞다.

그러나 validation에 E16을 포함하면 전체 오류 1273건 중 2↔3은 439건(34.5%)이고, **5→4가 557건**으로 가장 많다. 그중 542건은 E16이다. E16 포함/제외를 나누어 보고, 제외 점수만 전체 점수처럼 설명하면 안 된다.

## 2. 실행한 2↔3 보정

새 보정은 rules3 출력이 2 또는 3인 행만 수정한다. 기존 1/4/5/6 예측을 보존하고 용량별 t1 하한도 유지한다.

- **확인 상태 유지:** rules3가 3을 연속 10초 예측하면 이후 2 예측만 3으로 바꾼다. 15초보다 큰 관측 간격은 확인 중인 연속성을 끊는다. 미래 라벨·전환시각을 쓰지 않는다.
- **t1 상한:** fit의 용량별 실제 1·2단계 t1 누적 최고값 99.5% 분위수를 넘으면 기존 2를 3으로 바꾼다. 클로드의 보수적 상한과 같은 후보 기준이며 새로 분위수를 최적화하지 않았다.
- **두 규칙 결합:** 각 규칙의 증거를 원래 rules3에서 독립적으로 구해 합친다. 상한 규칙이 만든 3을 곧바로 연속 확인 증거로 누적시키지는 않는다.
- **온도별 soft 가중치:** 팀원이 이어서 분석한 용량×t1 구간별 2/3 log-odds 보정(alpha=0.5)을 fit 자료로만 추정했다. 2/3 판정 범위와 기존 하한을 보존했다.

| 방법 | dev F1 | validation 전체 F1 | validation E16 제외 F1 |
|---|---:|---:|---:|
| rules3 | 0.810150 | 0.728644 | 0.868530 |
| +3 확인 10초 | 0.814257 | 0.748698 | 0.869113 |
| +t1 상한 q99.5% | 0.813742 | 0.729103 | 0.869113 |
| **+확인 유지+t1 상한** | **0.817746** | **0.748904** | **0.869348** |
| +온도별 soft 보정 | 0.814213 | 0.714421 | 0.868928 |
| +soft 보정+확인 유지 | 0.814067 | 0.714592 | 0.869162 |

### 결합 보정의 정확한 이득과 한계

| | dev | validation 전체 | validation E16 제외 |
|---|---:|---:|---:|
| 고친 오답 | 59 | 209 | 7 |
| 기존 정답 훼손 | 0 | 0 | 0 |
| 2↔3 잔여 오류 | 365 | 230 | 210 |

validation의 수정 209건 중 **202건은 E16**, 나머지 7건은 다른 2개 실험이다. dev의 수정 59건은 5개 실험에 분산됐다. E16을 제외한 validation 개선은 **+0.0818%p**로 작다. 새로운 데이터에서 안전하다는 보장이 아니다.

실험 단위 paired bootstrap 2000회의 결합 보정 Macro F1 차이 구간:

- dev: `[+0.000876, +0.018319]`
- validation 전체: `[0, +0.053035]`
- validation E16 제외: `[0, +0.002268]`

개별 seed에 확인 유지 규칙을 붙이면 정답 훼손도 나온다. 현재 3-seed 앙상블에서의 결과를 다른 모델에 그대로 일반화하지 않는다. 관측 이력만 10초·15초 간격으로 성기게 한 확인에서도 결합 규칙의 정답 훼손은 0건이었으나, 15초에서는 dev 수정이 59→36건, validation 수정이 209→141건으로 줄었다.

### soft 가중치가 보여준 실패

온도별 soft 가중치는 dev에서 49건 수정/21건 훼손, E16 제외 validation에서는 42건 수정/39건 훼손이다. **E16에서 추가로 정답 165건을 훼손했다.** E16 제외 점수만 보면 이 악화를 놓친다. 이 후보를 제출 추천으로 채택하지 않는다.

## 3. 보정한 뒤 어떤 오류가 남나?

| 실제→예측 | dev: rules3→결합 보정 | validation E16 제외: rules3→결합 보정 |
|---|---:|---:|
| 3→2 | 275→216 | 168→161 |
| 2→3 | 149→149 | 49→49 |
| 5→6 | 50→50 | 111→111 |
| 6→5 | 45→45 | 53→53 |
| 5→4 | 61→61 | 15→15 |
| 4→5 | 26→26 | 33→33 |

**현재 보정은 이미 3일 가능성이 충분해진 뒤에도 2로 남는 오류를 줄인다. 실제 2인데 3을 너무 일찍 예측하는 198건(dev+E16 제외 validation)은 그대로다.** 2↔3 전체를 해결했다고 주장하지 않는다.

다음 2↔3 분석은 이 198건을 따로 다루어야 한다. 연속 확인 전의 3을 모두 2로 억제하는 단순 debounce는 이전 비교에서 실제 전환을 늦추며 정답을 훼손했으므로 그대로 적용하지 않는다. 현재 규칙의 방향을 뒤집어 상호 대칭인 물리 법칙처럼 사용해서도 안 된다.

## 4. 오류 수와 Macro F1 우선순위는 다르다

오류가 많은 쌍의 잠재 점수 이득도 더 클 것이라고 가정한 점을 수정했다. 해당 두 클래스 간 **오답만 실제 정답으로 교체하는 진단용 oracle**를 계산했다. 학습·추론 방법이 아니며 실제로 이만큼 개선할 수 있다는 예측도 아니다.

| 해당 쌍의 오답만 모두 수정한 가정 | dev 점수 이득 | validation E16 제외 점수 이득 |
|---|---:|---:|
| 2↔3 | +5.85%p | +2.71%p |
| 5↔6 | **+8.04%p** | **+7.84%p** |

표본이 작은 5·6단계의 F1을 각각 같은 비중으로 평균하기 때문에 적은 오류라도 점수 영향은 클 수 있다. **2↔3은 현재 작업으로 계속 줄이되, 다음 별도 개발 표적은 5↔6이 합리적**이다. 이미 확인한 열화상 하한을 즉시 추가한다는 뜻은 아니다. 그 규칙은 Test 변경이 한 실험에 몰린 기존 한계가 있다.

## 5. 클로드 기록에서 새로 확인하거나 제가 놓쳤던 사항

### 확인한 원본 기록

현재 프로젝트의 Claude 대화 기록(`cf55b404-0c22-4059-9d53-4e3900268de2.jsonl`)에서 사용자·assistant의 일반 텍스트를 확인했다. 마지막 기록은 호스트 UTC 기준 2026-11-14 15:44:52이며 첨부된 rules_robust 추천과 이어진다. 관련 scratch의 `bat_rules.py`, `rules_search2.py`, `tune.py`와 최신 팀원 `soft_23.py`, `soft_23_results.csv`, `residual_and_events.py`, `eval_34.py`, `rules_56_exceptions.csv`, `final_rules5.py`, 전역 단조 디코더 `monotone.py`도 읽었다. 다른 작업 폴더의 `b_stage_rules.py`, `soft_stage_prior.py`는 새 코드가 있다는 사실을 확인했으며 결과가 확인되지 않은 코드를 성능 개선으로 간주하지 않았다.

### 수정한 판단

1. **0.92/0.93 파일은 MLP가 아니다.** 실제 최종 코드는 원본 B 출력에 센서 규칙을 적용한다. 대화 중 'MLP 의존성 변경'이라는 설명과 제출 코드의 실체를 구분해야 한다.
2. **제 이전 stage23_audit는 45°C 규칙만 적용한 기준이었다.** rules3 기준의 잔여 오류와 섞어 설명한 점을 바로잡았다. 해당 보고서 상단에 후속 결과 링크를 붙인다.
3. **val 숫자가 서로 다른 이유도 확인했다.** 클로드의 비교는 fit 하한을 dev/validation에 공통 적용하여 0.868530(noE16)이었다. 팀원 일부 비교는 validation 하한을 Train 전체 78개 실험으로 재추정했다. 이번에 source를 바꾸면 validation 5행이 달라지고 모두 기존 정답을 훼손했다. 각각의 점수를 같은 조건의 결과처럼 비교하면 안 된다.
4. **추가 규칙 비교는 E16 제외가 대부분이었다.** soft 보정의 E16 훼손처럼 전체 점수에서 나타나는 실패가 가려질 수 있다. 이번 결과에는 항상 전체/제외 점수를 같이 저장했다.
5. **public으로 행별 정답과 실험 포함 여부를 확정한 기록은 검증 근거로 사용하지 않았다.** 사용자 보고 점수는 실제 성과 기록으로 존중하되, 집계 점수만으로 '38개 정답 행', 'T06만 public' 등을 확정하지 않았다. 이 추론으로 모델이나 후보를 고르지 않았다.
6. **t1 분위수는 라벨 정의가 아니라 경험적 제한이다.** 하한 1%가 실제 예외 없는 필요조건이라는 뜻은 아니다. 첫 45°C 교차 근거와 구분한다.
7. **첫 5행 전압 기준은 엄밀하게는 처음 몇 행의 미래값을 사용한다.** 배포 코드의 기존 동작을 보존했다. 현재/과거만 사용하는 구현과 비교했을 때 dev/validation에서는 전압 상태 및 출력 차이가 모두 0행이었다. 새 확인 유지 보정 자체는 미래를 사용하지 않는다.
8. **public 0.93 재현은 확인했지만 private 개선은 확인하지 못했다.** 새로운 독립 검증이나 private 정답 없이 결합 보정을 rules3보다 우수한 최종 제출이라고 단정하지 않는다.

## 결과와 다음 선택

이번 비교에서 가장 나은 연구 후보는 **rules3 + 확인 유지 + t1 상한**이다. 고정된 규칙을 다음 실험 단위 검증에서 평가할 대상으로 남긴다. 기존 0.93 제출 파일은 유지한다. E16 제외 validation 추가 이득이 작고 실험 수가 제한되어 있어 새 제출을 자동으로 대체하지 않았다.

`results_v2/`에는 전체/제외 점수, 오류 방향, 클래스별 오류, 실험별 수정·훼손, 바뀐 행의 원인, 개별 seed/간격 민감도, 임계값 source 차이, 기준 제출 재현 결과가 있다. 1/4/5/6 보존, t1 하한 유지, 독립 규칙 결합, 오류 방향 집계, 과거 불변성 등 **10개 테스트를 통과**했다.

재현:

```bash
/home/ubuntu/venv/bin/python rules3_stage23/evaluate.py --output rules3_stage23/results_new
/home/ubuntu/venv/bin/python -m rules3_stage23.cadence
/home/ubuntu/venv/bin/python -m unittest rules3_stage23.test_evaluate stage23_audit.test_analysis -v
```

`cadence.py`는 기존 `results_v2`에 스트레스 결과를 쓴다. 본 평가의 출력 폴더는 기존 것을 덮어쓰지 않는다. 이미 본 dev/validation에 대한 탐색 결과이며, full-system outer CV를 새로 수행한 결과는 아니다. 현 작업 브랜치는 기존 `feat/gahyun`을 유지했으며 이번 작업에서 checkout·commit·push하지 않았다.
